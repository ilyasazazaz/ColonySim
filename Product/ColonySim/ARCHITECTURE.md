# Архитектура тестового среза

## Принцип

Доменная симуляция не зависит от Unity API. Unity отвечает за запуск сценария, ввод и визуализацию, а изменение игрового состояния происходит только через явный `ColonySimulation.Step()`.

Текущий поток данных:

`IWorkPerformanceSource → ColonySimulation → INavigationMap / IReservationService → состояние Pawn и WorkTask → ColonyScenarioController`.

Каждый интерфейс существует потому, что в сценарии уже есть альтернативное поведение или отдельная ответственность. Остальные части пока остаются конкретными.

## Слои

### `ColonySim.Domain`

Сборка с `noEngineReferences: true`. Содержит игровые факты и правила:

- `Pawn`, `WorkTask`, `WorkAssignment`;
- дискретный цикл назначения, движения и выполнения;
- детерминированную сеточную навигацию;
- атомарное резервирование целей и ограниченных ресурсов;
- фабрику воспроизводимого демонстрационного сценария.

Её можно тестировать без сцены и без жизненного цикла `MonoBehaviour`.

### `ColonySim.Runtime`

Тонкий composition root для Unity:

- выбирает модель состояния до запуска симуляции;
- создаёт доменный сценарий;
- переводит `deltaTime` в явные дискретные шаги;
- отображает уже принятые доменом решения.

Контроллер не выбирает работу и не вычисляет её результат.

### `Tests`

EditMode-тесты закрепляют правила домена. PlayMode smoke-test проверяет только интеграцию сцены и адаптера Unity, не повторяя доменные тесты.

## Подтверждённые точки расширения

### Работоспособность: `IWorkPerformanceSource`

Минимальный контракт отвечает на один вопрос потребителя: может ли колонист выполнить набор функций и с какой скоростью. Сейчас есть две реализации:

- `SimpleCondition` — дешёвая агрегированная модель;
- `FunctionalCondition` — отдельные сознание, движение и манипуляция.

Новая модель здоровья должна реализовать этот контракт, если планировщику по-прежнему достаточно доступности, скорости и причины отказа. Сам интерфейс следует расширять только при появлении подтверждённого потребителя нового факта — например, качества результата, риска или особого способа передвижения.

### Пространство: `INavigationMap`

Симуляция просит путь, но не знает, хранится ли пространство сеткой, графом комнат или другим представлением. Текущая BFS-реализация достаточна для маленького статического сценария.

Переход к A*, кэшу путей или графу регионов оправдан только после появления размера карты, динамических препятствий или профилировочных данных. Эти изменения не должны менять модель работы.

### Владение: `IReservationService`

Резервирование отделяет выбор задания от атомарного владения целью и инструментом. Это предохраняет от двойных назначений и оставляет место для будущих составных ресурсов.

Расширять контракт стоит при появлении реальных требований: количества, таймаутов, приоритетного вытеснения или транзакции из нескольких заявок. Сейчас простой `ReservationBook` намеренно не моделирует склад.

## Следующие безопасные расширения

1. Ввести новый тип задания через данные `WorkTask`, пока цикл «дойти — выполнить» остаётся тем же.
2. Добавить изменение функционального состояния во времени и проверить освобождение резерва при отказе.
3. Выделить стратегию выбора заданий только тогда, когда появится второй реально тестируемый алгоритм.
4. Добавить DTO снимка и адаптер сохранения, когда состав сохраняемых фактов будет подтверждён. Unity-объекты не должны попадать в формат сохранения.
5. Исследовать переходы между детальной и агрегированной симуляцией отдельным экспериментом. Нельзя терять уже подтверждённые факты при понижении детализации.

## Что не следует добавлять заранее

- общий базовый класс для всех систем;
- сервис-локатор или DI-контейнер ради нескольких конструкторов;
- глобальный event bus вместо прямого потока данных;
- ScriptableObject как доменную модель живого состояния;
- ECS/DOTS до профилировки репрезентативной нагрузки;
- универсальные `Entity`, `Component`, `System` или граф действий без двух независимых потребителей.

Критерий простой: новая абстракция должна либо позволять заменить уже существующее поведение, либо защищать проверяемый инвариант. «Возможно пригодится» недостаточно.
