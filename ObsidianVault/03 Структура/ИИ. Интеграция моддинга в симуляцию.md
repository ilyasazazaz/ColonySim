## Factorio: фазы загрузки и изолированное состояние

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^002|М]]од Factorio определяется `info.json`, где указаны идентификатор, версия, совместимая версия игры и зависимости. Моды загружаются с учётом зависимостей. На старте игры проходят отдельные этапы настроек и прототипов; файлы `data.lua`, `data-updates.lua`, `data-final-fixes.lua` дают модам три последовательные возможности объявить или изменить прототипы. Эти файлы работают в общем Lua-состоянии этапа; после него прототипы фиксируются, и менять их во время игры нельзя. [Структура мода](https://lua-api.factorio.com/latest/auxiliary/mod-structure.html), [жизненный цикл](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html). ^002

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^003|И]]гровая логика Factorio находится в `control.lua`: каждый мод получает собственное Lua-состояние и подписывается на события. Сохраняемые данные лежат в отдельной для каждого мода таблице `storage`; она допускает сериализуемые значения, но не функции. При обновлении сохранения игра выполняет миграции JSON для переименования прототипов и Lua для изменения состояния. Сохранение помнит выполненные миграции. Это пример явного разделения определения типа, экземпляров в мире и версии сохранения. [Жизненный цикл](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html), [хранилище](https://lua-api.factorio.com/latest/auxiliary/storage.html), [миграции](https://lua-api.factorio.com/latest/auxiliary/migrations.html). ^003

## Minecraft Java: данные игры и программные моды

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^004|В]] Minecraft Java встроенные data packs добавляют или заменяют данные в пространствах имён: функции команд, рецепты, таблицы добычи и другие поддерживаемые типы. Порядок пакетов определяет, какие данные имеют приоритет; часть данных можно применить через `/reload`, но для отдельных реестров требуется полная перезагрузка мира. Это механизм расширения без собственного Java-кода. [Описание структуры пакета от Mojang](https://www.minecraft.net/fr-fr/article/minecraft-snapshot-17w43a), [примечание о перезагрузке реестров](https://www.minecraft.net/nl-nl/article/minecraft-java-edition-1-21-2). ^004

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^005|Д]]ля Java-кода сообщество использует загрузчики и API, например Fabric и NeoForge. В Fabric файл `fabric.mod.json` объявляет идентификатор, зависимости и точки входа; API предоставляет события и регистрацию содержимого. Событийный обработчик часто позволяет расширить поведение без прямого изменения внутренних классов, а mixin остаётся более глубоким вмешательством. Динамические реестры связывают уникальные идентификаторы с объектами и могут наполняться данными пакетов. Это отдельный слой поверх встроенных data packs; моды Fabric и NeoForge нельзя считать единым форматом. [Метаданные Fabric](https://docs.fabricmc.net/develop/loader/fabric-mod-json), [события](https://docs.fabricmc.net/develop/events), [динамические реестры](https://docs.fabricmc.net/develop/registries/dynamic-registry), [реестры NeoForge](https://docs.neoforged.net/docs/1.21.1/concepts/registries/). ^005

## RimWorld: определения, патчи и компоненты

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^006|R]]imWorld загружает метаданные мода из `About/About.xml` с `packageId`, зависимостями и подсказками порядка. Большая часть контента задаётся XML-определениями `Def`: например, `ThingDef` описывает тип объекта, а C# реализует его поведение. Наследование XML позволяет переиспользовать основу определения. Папки `Defs`, `Patches`, `Assemblies`, `Languages` и ресурсов разделяют данные, изменения данных, код и представление. Эти сведения приведены в документации сообщества моддеров, а не в официальной спецификации Ludeon. [About.xml](https://rimworldwiki.com/wiki/Modding_Tutorials/About.xml), [XML Defs](https://rimworldwiki.com/wiki/Modding_Tutorials/XML_Defs), [структура мода](https://rimworldwiki.com/wiki/Modding_Tutorials/Mod_Folder_Structure). ^006

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^007|P]]atchOperations RimWorld меняют узлы XML по XPath после загрузки определений, уменьшая необходимость целиком заменять чужой `Def`; результат всё равно зависит от порядка и условий патчей. Для поведения и состояния моддеры используют C# `ThingComp` с параметрами `CompProperties`: компонент создаётся для экземпляра объекта на основе списка компонентов в его `Def` и может сохранять данные. Здесь важно различать тип (`Def`) и состояние конкретной пешки или предмета (`ThingComp`). Прямое переписывание базовых определений и конфликтующие патчи остаются источниками несовместимости. [PatchOperations](https://rimworldwiki.com/wiki/Modding_Tutorials/PatchOperations), [ThingComp](https://rimworldwiki.com/wiki/Modding_Tutorials/ThingComp), [совместимость](https://rimworldwiki.com/wiki/Modding_Tutorials/Compatibility). ^007

## Что можно проверить в ColonySim

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^008|О]]бщий принцип трёх примеров — устойчивые идентификаторы, явные зависимости и разделение декларативного контента от исполняемого кода. Для задуманного редактора на телефоне разумно первым слоем сделать схемы сущностей, компонентов, ресурсов и поведения из разрешённых блоков. Проверка до запуска должна ловить отсутствующие ссылки, конфликты идентификаторов, циклы зависимостей и превышение бюджета мобильной симуляции. Это предложение, выведенное из сравнения, а не готовое решение для реализации. ^008

[[02 Корректура/ИИ. Интеграция моддинга в симуляцию#^009|Р]]асширение кодом стоит проектировать отдельно: ограниченные события и API, правила доступа к состоянию, сериализация, миграции и диагностика конфликтов. Испытательный набор: один новый предмет; пешка с новым свойством и событием; два мода, меняющих один тип; загрузка сохранения после переименования типа; отключение мода, у которого уже есть экземпляры в мире. Именно эти проверки покажут, где подходит сборка из пресетов, где нужен код и что должно происходить с существующей игрой. ^009
