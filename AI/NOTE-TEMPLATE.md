# Единая оболочка заметок 02–04
Применяют все исполнители. Содержание между панелью и «Для ИИ» определяется ролью; оболочка одинакова. Исправлять существующую заметку точечно, не перезаписывать её шаблоном.

## Порядок
1. Один YAML-frontmatter с первой строки.
2. Одна панель из примера ниже.
3. Содержание роли. У 04 сначала короткое «О карточке: …», затем разделы по источникам с исходными фрагментами, включая списки.
4. Один блок «Для ИИ» в самом конце.

Имя файла не содержит дату создания; она хранится только в created по WORKFLOW. Для 01 применяется только исключение created, а не эта оболочка с кнопками. Имя файла уже отображается Obsidian: не добавлять повторяющий его H1. Свойства смотреть в боковой панели, нижний блок свойств не создавать.

## Шаблон новой заметки
Это образец, не готовая заметка: все значения __...__ заменить. created — фактическая дата создания, rules_version — текущая версия из WORKFLOW.md после проверки. Пустые поля согласования допустимы только у новой заметки. Не сбрасывать их при миграции.

## Свойства без потерь
- parents — все реальные непосредственные источники. Потомки определяются обратными ссылками; отдельный children не нужен.
- Один источник: source_revision. Несколько: вместо него source_revisions со списком объектов path (путь от корня репозитория) и revision (сохранённая версия). Не хранить «см. раздел» и не выводить хеши в тело.
- Только в 04 добавить aliases: [] и kind: "краткая категория". Имя + aliases + kind + «О карточке» служат локальным словарём; отдельную копию описания в YAML не делать.
- Для подборок в 04/Нераспределённое действует та же оболочка; kind: нераспределённое, «О карточке» кратко обозначает остатки источника. Подборка не становится тематическим понятием.
- tags: 1–3 полезные тематические метки при наличии темы, без синонимических дублей. kind — классификация понятия, не статус проверки.
- Человеческие review_status, reviewed_at, reviewed_revision, reviewed_revision_format, review_changed_at, review_history, review_undo, review_base_commit/path, decision_status и неизвестные пользовательские свойства сохранять. Исполнитель не меняет согласование и не пересчитывает человеческий approved-хеш.
- Класс review-clean-pilot добавить один раз в существующий cssclasses, сохранив прочие классы. Общий CSS не копировать в каждую заметку.

Пример тела 04 для карточки «Пешка» (имена/якоря заменить реальными):
```md
О карточке: Упоминания отдельной действующей единицы симуляции; коллективы сюда не включаются без связи с отдельными **пешками**.

## [[03 Структура/Запись|Запись]]

> **[[03 Структура/Запись#^001|П]]ешка** входит во [[04 Справочник упоминаний/Фракция|фракцию]].
```
Тот же исходный фрагмент помещается в «Фракцию»: там слово «Пешка» может вести на её карточку, а «фракцию» — жирный текст без самоссылки. Видимые слова цитаты не менять; выделение собственного понятия определяется AGENT-3.md. Это пример прозы; исходный список сохраняется одним списком, а не отдельными блок-цитатами пунктов. Все фрагменты одного источника — в одном разделе, по порядку источника. Необходимую короткую добавленную подпись оформлять отдельной курсивной строкой с точным происхождением на первой букве; правила отбора, контекста и хронологии — AGENT-3.md.

## Проверка оболочки
YAML разбирается как отображение без повторных ключей; перед открывающим --- нет текста. Не заменять все --- в файле: это также разделители содержимого.
Считать фактические исполняемые вызовы review-buttons.js, в том числе вне маркеров: должен быть один. Комплект review-panel и review-feedback тоже по одному, парный.
Внутри feedback две горизонтальные линии — до заголовка и после комментария. Пустые строки отделяют маркер/заголовок/комментарий от линий, чтобы не возникал Markdown-заголовок. Старые дубли служебных линий снаружи удалить без затрагивания авторских разделителей.
Настоящие переносы строк, а не буквальные `n. Повторное применение шаблона идемпотентно. Проверить тело и человеческие свойства до/после, не удалять комментарий после выполнения пожелания.
Серые комментарии скрываются общим CSS в Live Preview; в исходном режиме доступны. Не удалять маркеры ради внешнего вида.

## Запросы и авторство ИИ
Оболочка кнопок не меняется. Для ИИ-результатов 01–03: source_kind: ai, request_origin: "[[03 Структура/Заметка#^010]]", при веб-поиске researched_at в ISO 8601. В 01 это разрешённое исключение к created; в теле короткая пометка «Материал ИИ». parents производных указывает предшествующий слой результата, а не исходный запрос. В 04 маркируется раздел ИИ-источника, а не всё авторство смешанной карточки.
В YAML заметки с запросами допускается ai_requests — список записей:
```yaml
ai_requests:
  - id: q001
    anchor: "^010"
    owner: requests
    status: новое
    revision: "__SHA256_ВИДИМОГО_ЗАПРОСА_И_КОНТЕКСТА__"
    result: []
    completed_at:
```
owner: requests, agent-1, agent-2, agent-3 или master. При нескольких заданиях в одном блоке добавь краткое task, не копию всей диктовки. result — реальные ссылки на результат/исправленный блок; при необходимости commit — проверенный SHA. history сохраняет прежнюю завершённую revision/result при изменении запроса. Неполное выполнение не отмечать как завершённое. Состояния запросов не меняют review_status и не заменяют человеческое согласование. Эта схема не требует специальных новых кнопок или плагина.
