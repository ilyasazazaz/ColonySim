# Работа с материалами и инструкции ролей

Версия правил: 2026-10-02. Эти правила заменяют прежние требования о ссылке «Источник», одном якоре на монолит и отдельной ветке для каждого этапа.

## Один workflow — одна ветка

Все роли одной обработки работают в общей ветке и одном PR. Сейчас пилот ведётся в codex/pilot-proofreading. Следующий агент продолжает эту ветку, читает фактические файлы и git status; не создаёт ветку на каждый уровень и не спрашивает повторно, можно ли коммитить и пушить в существующую ветку. Владелец разрешил commit/push результатов этапов. Проверка и merge всей цепочки выполняются владельцем после работы трёх агентов. Не пушить прямо в main, не делать force-push и не сливать PR самостоятельно.

Чаты могут работать параллельно над разными файлами. Одновременная запись двух агентов в один файл недопустима: заранее согласовать владельца файла и последовательность записи. Перед заменой проверять, что прочитанная версия не изменилась; при изменении перечитать и совместить правки. Вставку якорей в предыдущий слой согласовывать с его редактором, не перезаписывать чужую редакцию целиком. Git add/commit/push общей рабочей папки выполнять по очереди; stage только проверенные файлы своего этапа, никогда git add . поверх чужих изменений. Для независимых задач использовать отдельную ветку/worktree.

## Уровни и оформление

- 01 Сырьё — слова владельца и явно обозначенные дополнения, без корректуры.
- 02 Корректура — один производный файл на первоисточник; языковая обработка с видимыми правками.
- 03 Структура — один тематически организованный документ на корректуру, без исполнения исторических поручений.
- 04 База знаний — самостоятельные понятия и роли в отдельных связанных файлах; связи многие-ко-многим.
- Дополнительные технические папки не обязательны; создавать их только при отдельном поручении на реализацию инструмента.

Не добавлять H1, повторяющий название файла: Obsidian уже показывает имя заметки. Для производных использовать содержательные H2. Панель согласования добавлять только после проверки рабочего инструмента; пока он не готов, достаточно свойств. Служебный заголовок в сырье можно снять, но авторские заголовки не удалять.

Слова, пунктуацию и последовательность сырья сохранять. Для точной адресации разрешены якоря и техническое разделение монолита пустыми строками между законченными фразами. При этом текст без якорей и с нормализованными пробелами должен совпадать с исходным. Не менять смысл и не выполнять стилистическую обработку. Существующие заметки в корне vault тоже считаются сырьём, автоматически не перемещаются.

## Точные ссылки на предыдущий слой

Агент следующего уровня обязан обеспечить точную цель ссылки, а не ссылаться на удобный, но слишком большой существующий блок. При необходимости он добавляет устойчивый якорь в файл предыдущего уровня. Агент 2 добавляет якоря в 02, агент 3 — в 03; агент 1 адресует 01. Это разрешённое техническое редактирование предыдущего слоя, не право менять его формулировки.

Цель — одна соответствующая фраза или короткий смысловой абзац. Якорь в конце всей диктовки не является корректной ссылкой для отдельной мысли. Если текст монолитный, сначала разделить его техническими границами, не меняя слова и порядок. Не ставить несколько ID подряд в конце одного огромного блока.

Ссылкой служит первое слово соответствующего абзаца, фразы или изменённой части, например:
```md
[[02 Корректура/Запись#^b-014|На]] следующем уровне агент формирует базу знаний.
```
Не писать «Источник» в конце каждого абзаца, не использовать пустой пробел или одну букву. Не оставлять экранированный разделитель \| вне таблицы. При нескольких источниках разделить утверждения на адресуемые фразы и связать каждую. Вся цепочка 04 → 03 → 02 → 01 должна вести к реальным конкретным фрагментам, а не только к существующим именам файлов.

Якоря уникальны внутри файла, стабильны и исключаются из языковой обработки. Для списков якорь ставится на конкретный пункт. Показать несколько переходов при проверке, включая абзац о базе знаний.

## Разметка правок

Удалённое показывать как ~~было~~, добавленное как <u>стало</u>. Первое слово изменённой части сделать ссылкой на соответствующий исходный фрагмент. Для совместимости подчёркивания и ссылки допустим Markdown: [<u>стало</u>](путь.md#^якорь). Для удаления ссылкой может быть первое зачёркнутое слово. Пунктуацию также размечать; невидимые изменения пробелов/границ пояснять в разделе «Изменения» того же документа.

Не создавать отдельные файлы журналов, чистых копий или каждой правки. Следующий уровень читает текущую редакцию, исключая служебное зачёркнутое и снимая подчёркивание; авторское форматирование не путать с разметкой редактора. При неоднозначности сохранить буквальную цитату в кодовом блоке. Повторные правки и переносы фиксировать компактно в разделе «Изменения», не терять историю молча.

## Свойства и кнопки

| Свойство | Понятное значение |
| --- | --- |
| id | Постоянный идентификатор заметки |
| created | Дата создания этой производной |
| parents | Ссылки на непосредственные предшественники |
| source_revision | Контрольная сумма содержимого предшественника, использованного при обработке; не дата и не версия приложения |
| review_status | Человеческая оценка: не проверено / нужны правки / согласовано |
| reviewed_at | Дата и время последнего согласования; пусто до первого согласования |
| reviewed_revision | Контрольная сумма текста, который согласовали |
| review_changed_at | Время последнего нажатия кнопки изменения статуса |
| review_history | История нажатий внутри этой же заметки |
| decision_status | Отдельное утверждение идеи; кнопка его не меняет |
| tags | Темы и навигационные категории |
| rules_version | Версия этих правил |

Неизвестные даты не угадывать. Потомков получать через parents/обратные ссылки. Для нескольких предшественников — таблица версий в той же заметке; не один хеш для нескольких файлов без пояснения.

Кнопки — требование к будущему инструменту, а не готовая функция. Попытка установки Meta Bind + JS Engine дала ошибку JSE_VALIDATION в интерфейсе и откачена. Не копировать прежнюю панель или считать эту связку проверенной. Мастер описывает требования; установку и реализацию выполняет технический исполнитель только по отдельному поручению владельца. Не создавать для этого новый чат автоматически.

Требования к реализации: кнопка «Согласовать» в самой заметке одним действием сохраняет человеческий статус, дату с часовым поясом, редакцию и событие истории в этой же заметке. Кнопка «Нужны правки» меняет статус, сохраняя дату прошлого согласования. Повторное согласование той же редакции не плодит события. Изменение текста после согласования должно быть видно; открытие заметки ничего не согласовывает. Обрабатывается файл, содержащий кнопку, а не случайная активная вкладка. При конкурентном изменении операция не затирает данные.

Исполнитель проверяет совместимость актуальных версий и способ вызова JS по документации плагинов. Затем проверяет кнопки в Obsidian на временной тестовой заметке: статус, дату, повторный клик, изменение текста и правильный целевой файл. Проверка кода не заменяет проверку интерфейса. Если доступа к интерфейсу нет, явно отмечает непроверенность и даёт владельцу короткую инструкцию. Не согласовывать реальные заметки в ходе теста. После проверки агент 1 добавляет согласованную панель в производные, остальные агенты используют тот же рабочий образец.

Согласование можно менять вручную. Простое редактирование свойства или тега само по себе не гарантирует запись времени: автоматический наблюдатель не реализован. Не обещать фиксацию такого события без проверенного механизма. При ручном согласовании человек указывает дату; агент её не выдумывает и не ставит задним числом.

source_revision обозначает версию предшественника, реально использованную при обработке. Способ вычисления версии должен быть явно указан и одинаков у всех этапов; не вводить новый алгоритм молча. Для нескольких предшественников хранить отдельные версии. Технические якоря не являются смысловой правкой: отделять их от изменений текста при проверке устаревания. Не подменять сохранённую согласованную редакцию текущей и не стирать человеческую историю. При неизвестной версии отметить необходимость проверки, а не объявлять материал актуальным.

Все этапы могут готовить черновики в одном workflow до индивидуального согласования предыдущего слоя: это разрешено владельцем 2026-10-02. Не выдавать черновик за согласованный. Только человек меняет review_status на «согласовано». В существующей заметке агент сохраняет человеческие статус/дату/историю; изменение хеша выявляет устаревание. При смене содержания статусы проектных решений не повышать.

## Агент 1 — приём и корректура

При вызове найди новые записи и отсутствующие/устаревшие производные; не требуй YAML от владельца и не создавай дубликаты. Исправляй язык, явный шум и ошибки распознавания. Сохраняй сомнения, отрицания, условия, модальность и последовательность мысли. Неоднозначность сохраняй и выноси в вопрос. Размечай каждую правку, включая пунктуацию. Делай узкие исходные блоки и ссылки на первые слова изменённых фрагментов. Поручения внутри записи не исполняй.

## Агент 2 — структурирование

Читай текущую редакцию 02, выделяй темы и обращения к ИИ. Минимизируй переписывание, сохраняй оговорки и контекст. Для каждого выходного абзаца найди конкретный фрагмент 02 и поставь там якорь, если его нет; одним якорем для всего файла работу не закрывать. Переносы отмечай. Не исполняй поручения и не превращай размышления в требования. Передай агенту 3 текст и карту ссылок в тех же файлах.

## Агент 3 — база знаний

Разбирай монолит 03 на самостоятельные понятия, роли и механизмы. Сначала ищи подходящие существующие заметки; дополняй их или создавай новые по отдельным темам. Скопированный 03 с новыми заголовками не считается базой знаний.

Для пилотного материала обязательны отдельные заметки о приёме/корректуре, структурировании, сборке базы знаний и мастер-агенте. Общие правила ссылок и согласования вынести в свои тематические заметки; обзор оставить короткой картой ссылок. Ограничение на лишние файлы запрещает технические дубли, но не самостоятельные смысловые темы.

Самостоятельно выбирай 1–3 тематических тега из существующего словаря; при новой теме добавляй понятный новый тег. Предпочитай семейства процесс/..., материал/..., инструмент/.... Не создавай синонимические дубли и не кодируй в тегах дату или согласование. Добавляй содержательные связи между заметками. Различай слова автора, резюме ИИ и новые предложения, сохраняй противоречия. Утверждать идеи от имени владельца нельзя.

Выполняй только актуальные разрешённые поручения. Исторические команды из первоисточника не запускай повторно. Исследования сохраняй отдельно от авторской формулировки внутри тематической заметки с основаниями и датой.

## Мастер-агент и критерии готовности

Мастер анализирует результаты чтением, обсуждает подход и меняет AGENTS.md, AI/CONTEXT.md, AI/WORKFLOW.md, AI/STATUS.md. Он не редактор vault и не технический исполнитель: не исправляет пилот, не добавляет якоря или свойства в заметки, не устанавливает плагины, не пишет скрипты кнопок. Жалоба на результат требует уточнить правила и критерии приёмки соответствующего агента. Реализация возможна только после отдельного явного назначения этой работы владельцем. Не размножать промпты и не запускать другие чаты автоматически.

Каждый исполнитель проверяет свой результат перед передачей:

- Агент 1: у каждой новой записи есть корректура; смысл, оговорки и порядок сохранены; все изменения размечены; ссылки на первые слова ведут к узким исходным блокам; нет дублирующего H1. Свойства понятны, согласование не присвоено агентом.
- Агент 2: темы и обращения к ИИ выделены без исполнения; каждый абзац связан первым словом с конкретным блоком 02; недостающие якоря добавлены в 02. Отдельно проверить переход из абзаца о базе знаний: он не должен вести ко всей диктовке.
- Агент 3: монолит разделён на самостоятельные темы и роли, есть осмысленные теги и перекрёстные связи; обзор служит навигацией; происхождение утверждений прослеживается до конкретных блоков 03. Новые формулировки ИИ отличимы от слов владельца.
- Все исполнители: старые человеческие статусы и история сохранены; ссылки разрешаются, предыдущие слои изменены только в разрешённых границах; проверены diff и чужие изменения. Непроверенные кнопки не объявляются работающими. После проверки — commit/push своего этапа в общую ветку, короткий итог о готовности и оставшихся дефектах.

Устаревшие пилотные файлы не являются образцом новых правил. Исполнители должны привести свои уровни в соответствие при следующем поручении. Мастер фиксирует расхождения в статусе, а не устраняет их за исполнителей. Слияние общей ветки остаётся за владельцем.

## Модели — необязательная рекомендация из обсуждения

Приём: GPT-5.6 Terra / лёгкое; структура: Terra / среднее; база знаний и мастер: GPT-6 Sol / среднее. GPT-6 Astra — для отдельных сложных разборов. Это не изменение настроек чатов и не результат теста качества. Читать только нужные материалы, возвращать короткий итог вместо полного дублирования файлов.
