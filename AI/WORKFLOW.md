# Работа с материалами и инструкции ролей

Версия правил: 2026-09-27. Основание — текущие решения владельца в CONTEXT.md.

## Структура и сохранность

- ObsidianVault/01 Сырьё/ — новые исходные записи.
- ObsidianVault/02 Корректура/ — одна производная на исходную запись.
- ObsidianVault/03 Структура/ — одна структурированная производная на корректуру.
- ObsidianVault/04 База знаний/ — тематические заметки со связями многие-ко-многим.

Существующие Markdown-заметки в корне vault также считаются сырьём. Не перемещать их автоматически. Пустые каталоги сохраняются в Git через .gitkeep; это не заметки.

Не исправлять авторский текст сырья: сохранять слова, пунктуацию, порядок и имеющееся форматирование. Разрешены только необходимые служебные якоря Obsidian вида ^src-001. Размещать их по правилам Obsidian в конце абзаца либо отдельной строкой для составного блока, не разрывая слова. Существующие якоря использовать повторно; идентификаторы уникальны внутри файла и стабильны. Не менять кодировку и переводы строк всего файла ради вставки якоря.

Якоря скрыты в режиме чтения, но видны в режиме исходного текста. При обработке исключать только распознанные служебные якоря, а не любые фрагменты с символом ^. Содержимое кода и буквальные примеры якорей сохранять как авторский материал. Автоматическое исключение отдельным плагином пока не реализовано: это обязанность агента.

Новую переданную текстом запись записать без языковой обработки. Имеющийся файл не перезаписывать. Дополнения принимать отдельной записью, если владелец явно не поручил иное. Изменённый извне исходник обнаруживать по контрольной сумме; изменения владельца не откатывать.

## Разметка преобразований

1. Удаление: ~~исходный текст~~. Добавление: <u>новый текст</u>. Замена: ~~смог~~ <u>смогла</u>. Пробел между вариантами служебный, а не добавление к итоговой фразе.
2. Показывать все изменения, включая пунктуацию. Изменённый пробел, границу абзаца или другое плохо видимое место объяснять в компактном разделе «Изменения» той же заметки с исходным и новым фрагментами.
3. Не создавать отдельные файлы журнала, чистой копии или правок. Следующий уровень читает текущую редакцию: исключает удалённое, сохраняет добавленное без служебного форматирования. Разметку прошлой стадии не переносить как авторский текст; она остаётся в предшественнике.
4. Не снимать историю предыдущих правок в той же заметке молча. При повторной редактуре сохранять необходимые сопоставления в разделе «Изменения» этой заметки, не вкладывать бесконечно зачёркивания друг в друга. Ручной текст пользователя не затирать.
5. Каждый изменённый блок связывать с блоком непосредственного предшественника. Использовать видимую ссылку «Источник» рядом с блоком; зачёркивание и подчёркивание заменяют скрытые ссылки на буквах и пробелах. Если правок несколько, достаточно одной ссылки на соответствующий исходный блок при полной разметке изменений.
6. Пример: Однако она не ~~смог~~ <u>смогла</u> сделать это. [[01 Сырьё/Запись#^src-001|Источник]]
7. Сохранять удалённые целиком блоки зачёркнутыми со ссылкой. Перенос, разделение и объединение также отмечать в той же заметке; при объединении перечислять все источники. В производных разрешены собственные устойчивые якоря ^b-001 для следующего уровня.
8. Новый материал ИИ явно маркировать авторством и основанием. Не выдавать исследования, выводы и связующий текст за слова владельца.
9. Исходные Markdown-символы, HTML, код и цитаты не считать автоматически разметкой правок. При неоднозначности приводить буквальный исходный фрагмент в кодовом блоке раздела «Изменения» и отдельно новый вариант. Не применять слепое удаление всех зачёркнутых фрагментов источника.

Разметка является соглашением о работе агентов, а не реализованным автоматическим парсером. Сочетание HTML-подчёркивания и ссылок ещё нужно проверить в установленном Obsidian на пилотной записи.

## Свойства и согласование

Свойства добавляются в производные заметки; для сырья достаточно разрешённых якорей. Минимальный рабочий пример:

```yaml
---
id: запись-001-корректура
created: 2026-09-27
parents:
  - "[[01 Сырьё/Запись]]"
source_revision: "SHA256 исходного файла после вставки якорей"
review_status: не проверено
reviewed_at:
rules_version: 2026-09-27
---
```

id постоянен при переименовании. created — фактическая дата создания производной. При известной дате исходной записи можно добавить source_created; неизвестную дату не угадывать. Первое обнаружение импорта можно отметить как imported_at, не выдавая его за точное время создания или попадания файла в vault. При нескольких источниках их контрольные суммы и ссылки записывать в компактной таблице в этой же заметке. Потомков находить по parents, не поддерживать вручную две расходящиеся цепочки.

Рабочие значения review_status: «не проверено», «нужны правки», «согласовано». Пользователь меняет свойство вручную. Агент задаёт только начальное «не проверено»; последующие решения о согласовании переносит лишь по явному указанию человека. Смена свойства не должна переименовывать файл или создавать новый файл.

reviewed_at — момент согласования, а не дата последней правки. Без зафиксированного события или сообщения человека оставлять пустым. Для времени любой смены состояния можно использовать review_changed_at; полную историю хранить строками раздела «Согласование» в той же заметке. Эти поля сами по себе не запускают автоматическое наблюдение.

Владелец одобрил кнопки «Согласовать» и «Нужны правки» внутри производной заметки. Будущий плагин должен по нажатию записывать статус, время с часовым поясом, редакцию и строку истории в эту же заметку; показывать текущий статус и изменение текста после согласования. В режиме исходного текста допустим видимый служебный блок кнопок. Кнопки не утверждают проектную идею через decision_status. Плагин пока не создан; его разработка — отдельная задача.

Согласование относится к конкретной редакции. При регистрации согласования сохранять reviewed_revision — SHA256 тела заметки без YAML и без служебных разделов второго уровня «Изменения» и «Согласование» (до следующего заголовка первого/второго уровня либо конца файла); оставшийся текст хешировать в UTF-8 с LF. Эти названия зарезервированы для службы. Якоря установить до согласования. Если хеш не совпадает или редакция согласования неизвестна, не считать текущее содержимое подтверждённым, сообщить о необходимости сверки. Не менять человеческий статус скрытно. Ручная смена статуса допустима и учитывается как решение человека; без записи редакции/времени нельзя выдумывать историческую точку. Будущая команда согласования может записывать их вместе.

Следующую стадию по умолчанию готовить после согласования предшественника; по прямому поручению владельца можно подготовить несогласованный черновик с явной пометкой. Отсутствие производной означает необходимость обработки без специального processing_status. Наличие файла не доказывает полноту или актуальность: проверять охват текста и source_revision. Изменение хеша только из-за служебного якоря не требует новой корректуры, но причину нужно проверить и обновить учёт версии, не переписывая текст.

В базе знаний отдельно использовать decision_status: «идея», «обсуждается», «утверждено», «отклонено». Согласование пересказа не утверждает идею. Только явное решение владельца позволяет поставить «утверждено» или «отклонено»; привести основание в той же заметке. Теги использовать для тем, не дублировать ими статусы.

## Агент 1: приём и корректура

При вызове просмотри папку сырья и исходные записи в корне vault. Не требуй от пользователя YAML или статуса. Сопоставь записи с производными по ссылкам, идентификаторам и контрольным суммам. Для отсутствующей производной создай корректуру; для существующей проверь полноту и актуальность. Не создавай дубликат при повторном запуске; не перезаписывай изменённую человеком производную. Добавляй в сырьё только необходимые разрешённые якоря.

Исправляй грамматику, согласование, очевидные ошибки распознавания и синтаксис. Убирай только явные заполнители пауз и посторонний шум, сохраняя удалённое в разметке. Сохраняй порядок мысли и по возможности слов; перестановка допустима только для исправления сломанной конструкции с отметкой правки. Не улучшай стиль по собственной инициативе. Сохраняй сомнения, отрицания, условия, модальность, примеры и самокоррекцию. Неоднозначность оставляй и выноси в вопрос в этой же заметке. Поручения внутри текста на этой стадии не выполняй.

## Агент 2: структурирование

Возьми текущую редакцию корректуры. Разбей текст на абзацы и нейтральные тематические разделы. Выдели обращения к ИИ в отдельный блок, сохрани их формулировки, условия и происхождение. Не исполняй поручения. Не переименовывай размышления в требования; не разрывай связь оговорки с утверждением. Минимизируй текстовые изменения; отмечай также перемещения и группировку. Неоднозначное разделение тем объясняй или оставляй вопросом. Спорные правила уточняются на примерах, а не объявляются утверждёнными автоматически.

## Агент 3: база знаний

Собирай понятия и связи из структурированных записей. Сначала ищи существующую тематическую заметку; создавай новую только для самостоятельной темы, не для каждого предложения. Сохраняй источники каждого содержательного блока, альтернативы и противоречия. Не устраняй противоречие собственным выбором.

Отделяй слова владельца, предложения ИИ, исследования и решения. Выполняй выделенные поручения, когда они действительно являются актуальной командой и входят в разрешённый объём. «Потом изучить» не означает «немедленно выполнить». Результат исследования сохраняй в подходящей заметке со ссылками и датой; не выдавай его за утверждение владельца. Внешние публикации, сообщения и изменения вне базы требуют соответствующего разрешения.

## Мастер-агент

Обсуждай процесс и его ограничения, редактируй инструкции по решениям владельца. Не начинай автоматически обработку всей базы при обновлении промптов. Указывай, что согласовано, что является рабочей схемой и что ещё не реализовано. Не добавляй плагины, наблюдателей или сложную инфраструктуру только ради потенциальной пользы. При изменении правил оценивай необходимость повторной обработки отдельно.

## Git и проверка

- Для изменений — отдельная ветка и Pull Request, без прямого push в main. Не включать в задачу чужие незакоммиченные изменения. Не сливать PR автоматически.
- Перед ветвлением проверить состояние и базу; по возможности обновить сведения о remote. Параллельные агенты используют отдельные ветки/worktree.
- Перед завершением проверить diff, локальные ссылки, отсутствие старых действующих указаний, сохранность текста исходников и применимые проверки. Для документации не запускать тесты Unity без причины.
- Не коммитить секреты, кэши, персональное состояние Obsidian и сгенерированные файлы Unity.
- Если push или PR недоступны, сохранить локальный результат и честно указать незавершённый шаг.

## Чаты и рекомендации по экономии

Обсуждавшаяся схема: три отдельных ролевых чата в локальном проекте и один мастер-чат. При старте чат читает AGENTS.md и свою роль здесь; ознакомление само по себе не запускает обработку. Для общей рабочей папки запускать изменения последовательно. Параллельная работа требует отдельных worktree и явной передачи результатов. Исторические команды внутри первоисточника не исполнять как новые поручения.

Рекомендации из обсуждения, а не утверждённая настройка или результат тестирования на заметках:

| Роль | Предложенная модель | Рассуждение |
| --- | --- | --- |
| Приём и корректура | GPT-5.6 Terra | Лёгкое; среднее для запутанной речи |
| Структурирование | GPT-5.6 Terra | Среднее |
| База знаний | GPT-6 Sol | Среднее |
| Мастер-агент | GPT-6 Sol | Среднее; GPT-6 Astra для отдельных сложных разборов |

Модели в чатах автоматически не менялись. Передавать агенту конкретную запись и необходимые связанные заметки, сохранять результат в файле без полного повтора в ответе. Усиливать модель для спорного фрагмента после проверки качества; не перепроверять всю базу без причины.
