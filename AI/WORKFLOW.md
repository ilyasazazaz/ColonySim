# Рабочий процесс

## Git

1. Обновить локальный `main`.
2. Создать отдельную ветку: `feat/...`, `fix/...`, `docs/...`, `refactor/...`, `chore/...` или `experiment/...`.
3. Делать небольшие логические коммиты в формате Conventional Commits.
4. Запустить применимые проверки и просмотреть полный diff.
5. Открыть draft Pull Request с описанием цели, решения, рисков и проверок.
6. После проверки выполнить squash merge в `main` и удалить рабочую ветку.

Прямые push и force-push в `main` не используются.

## Несколько людей и агентов

- Одна задача принадлежит одной ветке и одному основному исполнителю.
- Параллельная работа ведётся в разных ветках или Git worktree.
- Перед изменением общих файлов проверить активные PR, чтобы не создавать конфликтующую редакцию.
- Передача работы происходит через описание PR: что сделано, что проверено, что осталось и какие решения требуются.
- GitHub Issues содержат задачи и критерии приёмки; `AI/STATUS.md` содержит только общий этап, а не список всех задач.

## Работа с контекстом

- Устойчивый подтверждённый факт обновляет `AI/CONTEXT.md`.
- Изменение процесса обновляет `AI/WORKFLOW.md` и при необходимости `AGENTS.md`.
- Изменение этапа или ближайшего результата обновляет `AI/STATUS.md`.
- Игровой дизайн, требования и исследования обновляют каноническую заметку в `ObsidianVault/`.
- Не сохранять историю разговоров целиком. Сохранять решение, основание и последствия.

## Исследование перед систематизацией

- Не начинать массовую редактуру с размножения текущих типов узлов. Сначала проверить, не смешивает ли классификация разные основания.
- Составить нейтральный вопрос без названий игр, уже приведённых владельцем.
- Найти внешнее решение и контрпример из разных предметных областей. Для технических утверждений предпочитать первичные материалы: документацию, статьи авторов моделей и разборы разработчиков.
- Отделить четыре слоя: явление мира, его вычислительную модель, игровой способ взаимодействия и программную организацию.
- До создания нового узла проверить, не является ли он ролью, параметром, вариантом или разделом более общего узла.
- После изменения просмотреть локальный граф ключевых заметок. Каждое заметное ребро должно позволять словами закончить фразу «этот узел ... тот узел».
- Не считать объём или единообразие признаком готовности. Допустимы короткое определение, таблица вариантов, разбор алгоритма, журнал эксперимента и полемическая заметка — в зависимости от содержания.

## Разбор систем и их реализаций

- Считать системой кандидата на включаемую область симуляции, а не только узкий класс с собственным хранилищем. Проверочный вопрос: меняется ли состав возможных процессов игры при ответе «этой системы нет».
- Отдельно фиксировать наличие системы, её тип, конкретную версию, глубину модели, пространственное представление и частоту обновления. Не называть все эти оси «версией».
- Для сравнения игр прослеживать цепочку `внутреннее состояние → промежуточные показатели → предоставляемый результат → потребляющая система`.
- Выводить интерфейс из реальных межсистемных вопросов и воздействий. Записывать, что система предоставляет, что требует, какой смысл имеет результат и какой отказ допустим.
- Допускать разные способы упаковки: одна комплексная система может реализовать несколько интерфейсов, которые в другой сборке предоставляют отдельные системы. Не переносить эту заменяемость автоматически в наследование программных классов.
- Перед утверждением формул или внутренней реализации чужой игры проверять первичные материалы или наиболее близкую к разработчикам документацию. Непроверенную реконструкцию помечать как гипотезу.

## Первая Unity-проба

- Перед архитектурной или продуктовой работой прочитать `AI/ARCHITECTURE_BRIEF.md` и применимые разделы `AI/ENGINEERING_MEMORY.md`.
- Вести пробу в отдельной ветке `experiment/...`; она не является молчаливым основанием для production-архитектуры.
- Использовать созданный владельцем проект `Product/ColonySim/` и зафиксированную им Unity 6000.5.9f1. Не переносить проект, не обновлять редактор или пакеты попутно без причины и проверки diff.
- Коммитить исходные assets, настройки проекта, packages и `.meta`; не коммитить `Library`, `Temp`, `Obj`, `Logs`, `UserSettings`, записи профилировщика и сборки.
- Использовать текстовую сериализацию Unity и видимые `.meta`, чтобы сцены, prefabs и ScriptableObject оставались проверяемыми в Git.
- Считать содержимое исходного `Packages/manifest.json` снимком шаблона Universal 2D, а не перечнем одобренных архитектурных средств. Подключение пакета к пробе должно следовать из сценария.
- Держать Unity lifecycle, ввод и представление у края. Предметные правила писать на обычном C#, когда это уменьшает стоимость теста и не порождает бессодержательные слои.
- Начинать с одного исполняемого тонкого среза. Не создавать по классу на каждый узел Obsidian и не реализовывать каталог систем по горизонтали.
- Вводить интерфейс после появления конкретного поставщика, потребителя и причины замены. Для первой пробы достаточно одной точки вариативности с двумя реализациями, выбираемыми до запуска.
- Не включать в исходный объём горячую замену, общий SML-движок, моддинг, сохранения, глобальную шину событий, сетевой слой и финальную мобильную оптимизацию.
- Проверять чистые правила Edit Mode tests, Unity-связку — Play Mode или smoke-сценарием. Случайность получает явный seed; скорость кадра не должна неявно определять предметный результат.
- В `Product/ColonySim/README.md` записать запуск, наблюдаемый сценарий, выбранные границы и намеренно отсутствующие возможности. В PR указать, какую гипотезу проба подтвердила или опровергла.

## Обучение по редактуре владельца

- При чтении Obsidian-заметки сначала проверить статусный тег в свойстве `tags`.
- Ровно один из тегов `ИИ`, `источник`, `редактировано`, `подтверждено` обозначает состояние рецензирования заметки. Эти теги взаимоисключающие.
- Для тега `ИИ` считать заметку агентским черновиком без редакторского одобрения владельца.
- Для тега `источник` считать содержательный текст прямым материалом владельца; добавленные агентом ссылки не меняют происхождение заметки.
- Для `редактировано` и `подтверждено` до выводов посмотреть `git diff -- <file>` и `git log --follow -p -- <file>`.
- Найти последнюю доступную версию с тегом `ИИ` и сравнить её с редактурой владельца.
- Различать правку языка, изменение структуры, изменение смысла и явное подтверждение решения.
- Тег `редактировано` является свидетельством личной правки, но не подтверждает автоматически весь оставшийся текст.
- Тег `подтверждено` является решением владельца в пределах содержания, которое он действительно просмотрел и утвердил.
- Повторно применимые выводы записывать в `AI/OWNER_MEMORY.md` со ссылкой на файл и Git-основание.
- Не обобщать единичную правку на весь проект без дополнительных свидетельств.
- Если исходная агентская версия отсутствует в Git, прямо отметить отсутствие базы сравнения и не реконструировать изменения по памяти.

## Авторство

GitHub-интеграции могут записывать автором подключённый аккаунт. Участие агента отмечается в описании PR или пользовательским trailer `Assisted-by: <agent>`. `Co-authored-by` используется только для реального аккаунта с принадлежащим ему email.

## Definition of Done

- запрос и критерии приёмки выполнены;
- отсутствуют случайные и несвязанные изменения;
- применимые тесты и проверки пройдены либо явно указано, почему они недоступны;
- документация обновлена вместе с изменением поведения;
- PR содержит понятный итог и известные риски;
- в репозиторий не попали секреты, кэши или персональное состояние инструментов.
