# Работа с материалами и инструкции ролей

Версия правил: 2026-10-03T00:31:33+03:00. Эти правила заменяют прежние требования о ссылке «Источник», одном якоре на монолит и отдельной ветке для каждого этапа.

## Версия правил

Версия — дата и время изменения действующих правил в ISO 8601 с секундами и часовым поясом Москвы: YYYY-MM-DDTHH:mm:ss+03:00. Каноническое значение указано в строке «Версия правил» этого документа. При содержательном изменении общих инструкций или роли мастер обновляет эту единую версию фактическим временем; агенты-исполнители не назначают собственные версии правил и не берут вместо неё время обработки заметки.

В YAML производной rules_version хранится строкой в кавычках; значение копируется из текущего WORKFLOW.md после содержательной проверки заметки. Прежние значения вида «2026-10-02.3», дата без времени, отсутствующее или отличающееся значение требуют проверки по текущим правилам. Не обновлять метки массово без проверки и не сбрасывать человеческое согласование. Время проверки заметки, версия исходника и дата человеческого согласования — отдельные понятия. При изменении правил во время прохода перечитать изменения и перепроверить затронутые результаты перед передачей; не помечать их новой версией автоматически.

## Один workflow — одна ветка

Все роли одной обработки работают в общей ветке и одном PR. Сейчас пилот ведётся в codex/pilot-proofreading. Следующий агент продолжает эту ветку, читает фактические файлы и git status; не создаёт ветку на каждый уровень и не спрашивает повторно, можно ли коммитить и пушить в существующую ветку. Владелец разрешил commit/push результатов этапов. Проверка и merge всей цепочки выполняются владельцем после работы трёх агентов. Не пушить прямо в main, не делать force-push и не сливать PR самостоятельно.

Чаты могут работать параллельно над разными файлами. Одновременная запись двух агентов в один файл недопустима: заранее согласовать владельца файла и последовательность записи. Перед заменой проверять, что прочитанная версия не изменилась; при изменении перечитать и совместить правки. Вставку якорей в предыдущий слой согласовывать с его редактором, не перезаписывать чужую редакцию целиком. Git add/commit/push общей рабочей папки выполнять по очереди; stage только проверенные файлы своего этапа, никогда git add . поверх чужих изменений. Для независимых задач использовать отдельную ветку/worktree.

## Полный проход по команде и отсутствие ложных ограничений

Команды «работай», «обработай», «продолжай» запускают полный проход назначенного уровня, а не только последнего упомянутого файла. Более узкое задание применяется только при явном ограничении владельца. Перед каждым запуском прочитать актуальные общие правила и свою роль полностью. Начальное «только ознакомься» не действует после поручения обработать материал. Рабочий репозиторий сейчас D:/ilyas/Projects/ColonySim; старый путь чата не основание остановиться.

Агент 1 рекурсивно перечисляет все Markdown-записи в «01 Сырьё» и оставшиеся авторские записи в корне vault; учитывает также неотслеживаемые Git файлы. Не включает служебные папки и уровни 02–04. Для каждого источника находит корректуру по parents/id и пути, а не только одинаковому имени; перемещение не должно создавать дубль. Сверяет весь уровень 02 с текущим источником И с текущими правилами, включая старые корректуры с тем же rules_version. Совпадение даты или наличие файла не доказывает готовность. Отсутствующие производные создаёт, устаревшие исправляет, соответствующие сохраняет без искусственных правок. После фактической проверки ставит rules_version из строки «Версия правил»; нельзя просто заменить метку версии.

Агенты 2 и 3 аналогично проверяют весь доступный вход своего уровня и существующие результаты: агент 2 — покрытие 02 → 03, агент 3 — покрытие всех смысловых тем 03 в 04, без требования «один источник — один файл» для базы знаний. Передача части готового входа не утверждает полноту предыдущего уровня. Незавершённые предшественники не использовать как готовые; независимые готовые материалы обрабатывать.

Исходные заголовки, строки «Инструменты», «Примеры», списки, абзацы и их порядок сохранять в корректуре разрешено без дополнительного подтверждения. Сохранение авторской структуры не является структурированием агентом 2. Агент 1 не придумывает новую тематическую структуру, но и не удаляет существующую. Запрет дублирующего H1 касается добавленного агентом заголовка, а не права уничтожить авторский текст. Правильный исходный текст допускает корректуру без языковых изменений. Явные опечатки исправлять с разметкой; неоднозначность кратко отмечать, сохраняя оригинал, и продолжать остальную работу. Не требовать разрешения на буквальное копирование источника, отсутствие YAML, черновой статус или обычную правку своей роли. Отсутствующая кнопка согласования не блокирует обработку.

Перед завершением повторно сверить весь вход с выходом. Отчитаться численно: найдено, создано, обновлено, проверено без изменений, осталось; перечислить каждый остаток и конкретную причину. Один сложный файл не останавливает остальные. Пока есть доступные необработанные файлы, не завершать ответом «запомнил», обещанием продолжить или вопросом о разрешённой работе. Прерванный проход возобновлять с остатка, проверяя уже сделанное; не объявлять частичный результат полным.

Реальный отказ автоматической проверки не обходить другим инструментом и не выдавать за обычное правило проекта. Прочитать точную причину, проверить фактический источник и допустимый более узкий способ работы. Если причина не показана, так и сказать, не приписывать проверке предположения. При неустранимом отказе зафиксировать конкретный файл, действие и полученную причину, выполнить независимую работу и запросить только необходимое разрешение на действительно заблокированное действие. Эта инструкция уточняет роль и не отключает внешние ограничения.

## Передача между существующими чатами

Владелец прямо разрешил 2026-10-02 запуск агента 1 и автоматическую передачу заданий после завершения: Агент 1 → Агент 2 → Агент 3. Это разрешение на сообщения в существующие чаты этой цепочки, а не на создание новых чатов, бесконечные перезапуски или переписку с посторонними. Основание — сообщение владельца в чате «Мастер агент» 01a0e441-28cb-7003-95d7-17489418be2e: «После этого, дай ему команду, о запуске работы. Так же явно пропиши в поведении агентов правила передачи задания следующему агенту при завершении». При необходимости проверить его через read_thread.

Чаты на host local: «Агент 1» пересоздаётся владельцем: старый чат 01a0e46e-d622-7c42-8bcd-2cf888f97d21 выведен из маршрута, не отправлять ему задания; новый адрес — чат, которому владелец явно назначит эту роль; «Агент 2» — 01a0f940-c0bb-7ad2-9157-16be281c4189; «Агент 3» — 01a0f942-2f41-7373-bc67-34eb4d402147. Перед отправкой проверить существование адресата через список чатов; не подбирать случайный чат с похожим названием.

По завершении проверки и commit/push своего этапа агент 1 отправляет задание агенту 2, агент 2 — агенту 3 через send_message_to_thread. Сообщение содержит рабочий путь, ветку, коммит, версию правил, готовые входные файлы, оставшиеся блокировки и команду выполнить полный проход своего уровня. Получатель перечитывает правила и реальные файлы, а не ограничивается обещанием или перечисленным последним файлом. Сохраняется разделение ролей: передавший не делает следующий этап сам.

Если отдельные записи реально заблокированы, завершить все независимые и передать только проверенный доступный результат с явной пометкой неполноты; блокировки не скрывать. Успешную передачу подтверждает ответ инструмента, а не фраза «передал». Если инструмент недоступен или отказал, сообщить об этом и дать готовый текст передачи. Не считать сообщение подтверждением завершения следующего этапа.

Один сигнал на готовый пакет; не слать повтор того же коммита и набора файлов. Если изменений нет, передавать дальше лишь при известной незавершённой работе следующего уровня или ещё не переданном пакете. Агент 3 завершает цепочку отчётом владельцу в своём чате; не запускает цепочку обратно. На один файл одновременно — один редактор; перед якорями в предшественнике проверять свежесть и текущую занятость. Все Git-операции в общей папке последовательны, чужое staged не коммитить. Человеческое согласование и merge остаются за владельцем и не являются условием передачи черновиков.

## Уровни и оформление

- 01 Сырьё — слова владельца и явно обозначенные дополнения, без корректуры.
- 02 Корректура — один производный файл на первоисточник; языковая обработка с видимыми правками.
- 03 Структура — один тематически организованный документ на корректуру, без исполнения исторических поручений.
- 04 База знаний — самостоятельные понятия и роли в отдельных связанных файлах; связи многие-ко-многим.
- Дополнительные технические папки не обязательны; создавать их только при отдельном поручении на реализацию инструмента.

Не добавлять H1, повторяющий название файла: Obsidian уже показывает имя заметки. Для производных использовать содержательные H2. Панель согласования добавлять только после проверки рабочего инструмента; пока он не готов, достаточно свойств. Служебный заголовок в сырье можно снять, но авторские заголовки не удалять.

Слова, пунктуацию и последовательность сырья сохранять. Для точной адресации разрешены якоря и техническое разделение монолита пустыми строками между законченными фразами. При этом текст без якорей и с нормализованными пробелами должен совпадать с исходным. Не менять смысл и не выполнять стилистическую обработку. Существующие заметки в корне vault тоже считаются сырьём, автоматически не перемещаются.

## Точные ссылки на предыдущий слой

Агент следующего уровня обязан обеспечить точную цель ссылки, а не ссылаться на удобный, но слишком большой существующий блок. При необходимости он добавляет устойчивый якорь в файл предыдущего уровня. Агент 2 добавляет якоря в 02, агент 3 — в 03; агент 1 адресует 01. Это разрешённое техническое редактирование предыдущего слоя, не право менять его формулировки.

Цель — одна соответствующая фраза или короткий смысловой абзац. Якорь в конце всей диктовки не является корректной ссылкой для отдельной мысли. Если текст монолитный, сначала разделить его техническими границами, не меняя слова и порядок. Не ставить несколько ID подряд в конце одного огромного блока.

Ссылкой служит первое слово соответствующего абзаца, фразы или изменённой части, например:
```md
[[02 Корректура/Запись#^b-014|На]] следующем уровне агент формирует базу знаний.
```
Не писать «Источник» в конце каждого абзаца, не использовать пустой пробел или одну букву. Не оставлять экранированный разделитель \| вне таблицы. При нескольких источниках разделить утверждения на адресуемые фразы и связать каждую. Вся цепочка 04 → 03 → 02 → 01 должна вести к реальным конкретным фрагментам, а не только к существующим именам файлов.

Якоря уникальны внутри файла, стабильны и исключаются из языковой обработки. Для списков якорь ставится на конкретный пункт. Показать несколько переходов при проверке, включая абзац о базе знаний.

## Разметка правок

Удалённое показывать как ~~было~~, добавленное как <u>стало</u>. Первое слово изменённой части сделать ссылкой на соответствующий исходный фрагмент. Для совместимости подчёркивания и ссылки допустим Markdown: [<u>стало</u>](путь.md#^якорь). Для удаления ссылкой может быть первое зачёркнутое слово. Пунктуацию также размечать; невидимые изменения пробелов/границ пояснять в разделе «Изменения» того же документа.

Не создавать отдельные файлы журналов, чистых копий или каждой правки. Следующий уровень читает текущую редакцию, исключая служебное зачёркнутое и снимая подчёркивание; авторское форматирование не путать с разметкой редактора. При неоднозначности сохранить буквальную цитату в кодовом блоке. Повторные правки и переносы фиксировать компактно в разделе «Изменения», не терять историю молча.

## Расположение свойств и применение кнопок

По уточнению владельца: в начале видимого содержимого производных 02–04 находятся кнопки, затем текст, в самом конце — блок «Свойства» с понятными названиями полей и историей согласования. Сырьё панелями не дополнять. Не переносить YAML frontmatter в хвост: Obsidian распознаёт его только в начале файла. Для сохранения нативных тегов и свойств оставить единственное машинное хранилище в YAML, скрыть его верхнее отображение и выводить значения в нижнем блоке из того же хранилища. Не заводить вторую независимо редактируемую копию данных. Требуемый вид проверить в чтении и Live Preview; в исходном режиме технический YAML остаётся сверху. Основание: https://help.obsidian.md/properties.

Агент 1 отвечает за доведение общей механики и рабочего образца кнопок в рамках нынешнего поручения, не перекладывая это обратно на мастера. Использовать общий исходник AI/review-buttons.js и шаблон AI/REVIEW-BUTTONS.md. Старую реализацию из Git не развёртывать. Способ подключения обновлён; перед объявлением готовности необходима проверка в Obsidian. Не восстанавливать старые плагины и заметки целиком. Сохранить согласованную механику: две кнопки, дата и версия при согласовании, история, защита чужих изменений, отсутствие повторных событий, привязка к своей заметке. Изменение служебных свойств и нижнего блока не должно само делать согласованный текст устаревшим. Агенты 2 и 3 используют один общий механизм без собственных вариантов. Недоступность кнопки не останавливает обработку текстов; в отчёте разделять готовность текста и инструмента.

## Свойства и кнопки

| Свойство | Понятное значение |
| --- | --- |
| id | Постоянный идентификатор заметки |
| created | Дата создания этой производной |
| parents | Ссылки на непосредственные предшественники |
| source_revision | Контрольная сумма содержимого предшественника, использованного при обработке; не дата и не версия приложения |
| review_status | Человеческая оценка: не проверено / нужны правки / согласовано |
| reviewed_at | Дата и время последнего согласования; пусто до первого согласования |
| reviewed_revision | Контрольная сумма текста, который согласовали |
| review_changed_at | Время последнего нажатия кнопки изменения статуса |
| review_history | История нажатий внутри этой же заметки |
| decision_status | Отдельное утверждение идеи; кнопка его не меняет |
| tags | Темы и навигационные категории |
| rules_version | Версия этих правил |

Неизвестные даты не угадывать. Потомков получать через parents/обратные ссылки. Для нескольких предшественников — таблица версий в той же заметке; не один хеш для нескольких файлов без пояснения.

Общий скрипт кнопок сохранён в AI/review-buttons.js; применение обязательно по AI/REVIEW-BUTTONS.md. Логика проверяется изолированно, развёртывание и UI-проверку выполняют агенты своих уровней. Попытка установки Meta Bind + JS Engine дала ошибку JSE_VALIDATION в интерфейсе и откачена. Не копировать прежнюю панель или считать эту связку проверенной. Мастер описывает требования; общую механику кнопок по текущему поручению владельца доводит агент 1, остальные агенты применяют проверенный образец. Не создавать для этого новый чат автоматически.

Требования к реализации: кнопка «Согласовать» в самой заметке одним действием сохраняет человеческий статус, дату с часовым поясом, редакцию и событие истории в этой же заметке. Кнопка «Нужны правки» меняет статус, сохраняя дату прошлого согласования. Повторное согласование той же редакции не плодит события. Изменение текста после согласования должно быть видно; открытие заметки ничего не согласовывает. Обрабатывается файл, содержащий кнопку, а не случайная активная вкладка. При конкурентном изменении операция не затирает данные.

Исполнитель проверяет совместимость актуальных версий и способ вызова JS по документации плагинов. Затем проверяет кнопки в Obsidian на временной тестовой заметке: статус, дату, повторный клик, изменение текста и правильный целевой файл. Проверка кода не заменяет проверку интерфейса. Если доступа к интерфейсу нет, явно отмечает непроверенность и даёт владельцу короткую инструкцию. Не согласовывать реальные заметки в ходе теста. После проверки агент 1 добавляет панель в свои производные, агенты 2 и 3 — в свои. Корректура содержит собственный полный текст проверенной редакции. Встраивание ![[01 Сырьё/...]], ссылка на исходник, пустой шаблон или одни свойства не заменяют корректуру. Они автоматически считаются незавершённой работой независимо от совпадения числа файлов и rules_version. Если языковых правок не требуется, всё равно сохранить самостоятельный проверенный текст. Рабочая очередь ведётся в рамках задачи, без новых файлов-журналов. После прерывания сверить фактическое состояние и продолжить остаток. Реальные отказы инструментов обрабатывать по общему разделу: не обходить, не выдумывать причину, выполнять доступную независимую работу. Финальный ответ не запускает фоновую обработку.

### Две ссылки в одном слове на уровне 04

Если слово должно одновременно указывать на источник утверждения и на другую карточку базы знаний, первая буква ведёт к точному фрагменту предыдущего слоя 03, остальная часть слова — к карточке 04. Между частями слова нет пробела. Пример:

```md
[[03 Структура/Колонии#^001|К]][[04 База знаний/Колония|олония]]
```

Если нужен конкретный сегмент карточки 04, использовать реально существующий якорь:

```md
[[03 Структура/Колонии#^001|К]][[04 База знаний/Колония#^002|олония]]
```

Это исключение для уровня 04 из прежнего запрета ссылки на одну букву. Источник — непосредственный предшественник 03, далее сохраняется цепочка 03 → 02 → 01; не заменять ссылку на происхождение ссылкой на связанную тему. Если второй ссылки на карточку нет, для происхождения остаётся первое слово. Не разрезать однобуквенное слово на пустые ссылки: выбрать другое подходящее слово фрагмента для источника, сохранив отдельную тематическую ссылку. Видимый текст и написание слов не менять.

Несколько последовательных строк или пунктов, взятых из одного непрерывного фрагмента источника в том же порядке, получают одну ссылку на источник в начале группы. Не повторять источник у каждой соседней строки автоматически.

Группа ограничена одним понятным смысловым фрагментом и конкретной целью в 03. Смена источника, пропуск несмежного материала, перестановка, вставка нового вывода или новая самостоятельная тема требуют новой привязки. Заголовок или граница списка завершают группу; не распространять ссылку неявно на остальную заметку. Удалять только известный служебный блок между review-properties:start и review-properties:end либо однозначно распознанный старый генератор свойств. Не удалять авторский текст, замечания для ИИ или любой раздел только из-за заголовка «Свойства». Это изменение заменяет прежнее требование выводить свойства внизу. До команды выпуска заметки и скрипт не мигрировать.

### Коммиты результата и обратная связь владельца

Каждый агент завершает проверенный этап отдельным коммитом своих изменений и push в общую рабочую ветку перед передачей. Коммит может содержать несколько обработанных заметок одного этапа; отдельная ветка или коммит на каждый файл не требуется. Не включать посторонние изменения владельца и других агентов. Технические изменения предыдущего слоя, включая якоря, также должны быть явно учтены. Зафиксированный результат — опорная редакция для сравнения, а не произвольный предыдущий коммит всей ветки.

Кнопки: «Согласовать», «Исправлено мной», «Нужны правки» и «Отменить действие». «Исправлено мной» означает, что владелец внёс изменения и считает текущий результат подходящим; сохраняются статус, время, контрольная сумма текущего текста и опорная версия агента. После последующих изменений показывать, что текст изменился после отметки. «Отменить действие» восстанавливает предыдущее состояние согласования, сохраняя текст и комментарий; история отмены не стирается.

Для сравнения использовать Git без отдельных файлов-снимков и без обязательного автоматического коммита при нажатии кнопки. Связь с результатом агента хранить как agent_revision (полный SHA коммита) и при необходимости agent_revision_path (путь заметки в этом коммите). Эти данные должна заполнять реализация передачи: сначала коммит результата, затем запись его известного SHA в свойства; при необходимости последующий служебный коммит закрепляет только эту привязку, не подменяя базовый SHA. Нельзя пытаться записать в коммит его собственный будущий SHA. При нажатии «Исправлено мной» сохранять текущую привязку отдельно как review_base_commit и review_base_path, чтобы следующая обработка не сместила базу уже полученной обратной связи. Не выбирать базу по последнему коммиту ветки или времени файла. Если SHA не задан, сначала установить его по истории обработки; неоднозначность явно отметить.

Мастер сравнивает текст опорной редакции с фактической текущей редакцией владельца. Это сравнение на момент анализа, а не обещание восстановить точное состояние на момент нажатия: хеш не хранит текст. Если текст изменился после отметки, явно указать это и анализировать актуальную редакцию. До анализа очередной исполнитель сохраняет найденные пользовательские изменения и не поглощает их новой опорной версией молча; при необходимости фиксирует их отдельным коммитом с явным происхождением перед своей переработкой. Наличие такой обратной связи не останавливает независимые записи.

По соглашению владельца содержательные изменения после зафиксированного результата агента считаются его обратной связью, если нет свидетельств другого происхождения. Сам Git diff не доказывает авторство: исключать известные служебные изменения кнопок, якорей, свойств и изменения других агентов; смешанные или неоднозначные правки не приписывать владельцу уверенно. Содержательные правки и предпочтения оформления анализировать отдельно.

Анализ человеческих исправлений и предложения к поведению агентов выполняет мастер, не исполнители уровней. Формат разбора: что изменилось → предположение о цели владельца → предлагаемое изменение инструкции с примером. Предположение явно обозначать и предоставлять владельцу возможность поправить его. Различать единичную правку конкретной мысли и устойчивое предпочтение; не менять автоматически глобальные правила по одной правке. Предложения накапливать для обсуждения и общего выпуска.

### Блок «Для ИИ»

В конце заметки предусмотреть один блок «Для ИИ», отделённый горизонтальными линиями. Это нейтральная обратная связь: замечания, пожелания, понравившаяся идея, удачный пример. Комментарий не означает отрицательную оценку и сам по себе не меняет статус согласования. Владелец может заполнить его при любом статусе. Кнопка «Нужны правки» создаёт блок, если его нет, либо открывает существующий, не плодя дубликаты; блок можно также добавить вручную без смены статуса.

Нажатие не отправляет поручение немедленно: пользователь ещё должен написать комментарий. Отправка по отдельной команде владельца или согласованному выпуску пакета. Повторное нажатие и отмена статуса не удаляют комментарий. Блок — служебная обратная связь, не авторский материал для переноса в следующие уровни. Его изменения не должны сами отменять согласование основного текста; при реализации использовать явные служебные границы, не исключать произвольный авторский раздел только по заголовку.
